# PAAR Worklog

사용자가 실제로 한 업무를 채용·평가 자료로 재사용 가능한 PAAR 기록으로 만든다.
이 문서는 나중에 이력서와 면접 답변의 원천이 되므로, **읽는 사람이 검증할 수 있는
사실만 담는 것**이 최우선이다. 그럴듯하게 쓰는 것보다 틀리지 않게 쓰는 것이 중요하다.

## PAAR 정의

사용자가 정한 형식이며 임의로 바꾸지 않는다.

| 항목 | 이름 | 담아야 하는 것 |
|---|---|---|
| P | Problem | 비즈니스 임팩트가 있는 문제 |
| A | Analyze | 왜 이 방법을 택했나 (trade-off 고려) |
| A | Action | 실제로 뭘 했나 |
| R | Result | 수치로 검증된 결과 |

각 항목의 기준:

- **Problem** — 기술 현상으로 끝내지 않는다. "타입 힌트가 없다"는 현상이고,
  "프론트 생성 타입이 런타임과 어긋나 배포 후 버그로 드러난다"가 문제다.
  누가·무엇을 손해 보는지(사용자, 비용, 개발 속도, 장애 위험)가 한 문장에 드러나야 한다.
- **Analyze** — 선택한 안만 쓰면 실패다. 검토한 대안, 버린 이유, 감수한 손실을 함께 쓴다.
  대안이 실제로 없었다면 "대안 없음"이라고 쓰고 왜 없었는지 밝힌다. 억지로 만들지 않는다.
- **Action** — 파일·워크플로·커밋 단위로 구체적으로 쓴다. 추상적인 동사("개선했다",
  "최적화했다")만 있으면 다시 쓴다.
- **Result** — 수치가 원칙이다. 수치가 없으면 [수치 없는 결과](#수치-없는-결과) 규칙을 따른다.

## 절대 하지 않는 것

1. **수치를 추정하거나 만들지 않는다.** "약 30% 개선" 같은 문장을 근거 없이 쓰지 않는다.
   측정값이 없으면 없다고 쓴다.
2. **하지 않은 일을 쓰지 않는다.** 커밋·PR·파일로 확인되지 않은 Action 은 제외하거나
   사용자에게 물어 확인한다.
3. **확인 없이 Notion 에 쓰지 않는다.** 초안을 대화에 먼저 보여주고 승인받는다.
4. **기존 페이지 내용을 덮어쓰지 않는다.** append 만 한다. `replace_content` 는 쓰지 않는다.
5. **작성한 PAAR 본문을 레포에 저장하지 않는다.** 본문에는 회사 내부 의사결정과
   아키텍처가 들어간다. 초안은 대화에만 두고, 승인된 최종본은 Notion 에만 쓴다.
   사용자가 파일로 달라고 하면 저장 경로가 공개 레포가 아닌지 확인한 뒤 저장한다.
   이 규칙은 PAAR 본문에만 적용되며, 이 스킬 문서 자체는 해당하지 않는다.

## 작업 흐름

### 1. 대상 범위 확정

무엇에 대한 기록인지 확정한다. 다음 중 하나로 좁혀지면 충분하다.

- PR 번호 또는 URL
- 브랜치명
- 커밋 범위
- 기간 (예: 7/21 ~ 7/28)

대화 맥락에서 이미 명확하면 묻지 않는다. 방금 작업한 내용을 정리하라는 요청이면
현재 브랜치와 최근 커밋을 대상으로 삼는다. 전혀 단서가 없을 때만 한 번 묻는다.

### 2. 근거 수집

추측하지 말고 실제 이력을 읽는다.

```bash
git log --oneline --no-merges <기본브랜치>..HEAD   # 기본브랜치는 레포마다 확인
git log --stat -n 20 --no-merges
gh pr view <번호> --json title,body,files,comments,mergedAt
gh pr list --state merged --limit 20 --json number,title,mergedAt,headRefName
```

변경 규모가 큰 파일은 실제로 열어 무엇이 바뀌었는지 확인한다. PR 본문과 리뷰 코멘트에
의사결정 근거가 남아 있는 경우가 많으므로 반드시 읽는다.

Analyze 에 쓸 trade-off 는 대개 PR 본문·리뷰 스레드·ADR 문서에 있다. 레포에 ADR
디렉터리가 있으면 함께 읽는다. 코드만 보고 의도를 추측해 쓰지 않는다.

### 3. 수치 확보

Result 에 쓸 수치를 찾는다. 후보:

- CI 실행 시간, 테스트 수, 커버리지 변화
- 응답 시간, 쿼리 수, 페이로드 크기
- 처리 건수, 에러율, 재시도 횟수
- 수정한 결함 건수, 차단한 케이스 수
- 절감한 비용, 줄인 수작업 시간

로그·CI 결과·스크립트로 확인 가능한 것은 직접 확인한다. 확인이 불가능하면 사용자에게
"이 수치를 아시나요"라고 구체적으로 묻는다. 막연히 "수치 있나요"라고 묻지 않는다.

#### 수치 없는 결과

측정값이 없다면 다음 순서로 처리한다.

1. **검증 가능한 사실로 대체** — "필드 삭제 → 🚨 알림, 추가 → 📝 알림을 실제 재현해 확인"
   처럼 재현으로 입증한 동작을 쓴다. 수치는 아니지만 검증 가능하다.
2. **측정 미실시 명시** — 그것도 없으면 `- 정량 측정: 미실시` 로 남긴다. 빈칸으로 두거나
   그럴듯한 문장으로 채우지 않는다.

측정 미실시가 반복되면 초안 전달 시 짧게 지적한다. 다음 업무에서 무엇을 미리 측정해
두면 좋을지 한 줄로 제안한다.

### 4. 초안 작성

아래 서식을 따른다. 한국어, 개조식, 과장 없는 서술.

```markdown
## <업무 제목>

**기간** <시작> ~ <종료> · **PR** #<번호> · **범위** <서비스/디렉터리>

### P — Problem
- <비즈니스 임팩트가 드러나는 문제 한두 줄>
- <문제가 방치될 때의 결과>

### A — Analyze
1. <의사결정 주제> → <선택> : <이유>. 버린 안은 <대안>이며 <버린 이유>.
2. ...

### A — Action
- <파일/워크플로>: <무엇을 어떻게>
- ...

### R — Result
- <수치로 검증된 결과>
- <재현으로 확인한 동작>
- 정량 측정: 미실시  ← 수치가 없을 때만
```

분량 기준: Analyze 는 의사결정 3개 이상이면 충분하고, 전체가 화면 한 장을 크게
넘지 않게 한다. 길이보다 각 항목이 검증 가능한지가 중요하다.

제목은 결과가 드러나게 쓴다. "CI 개선" 처럼 뭉뚱그리지 않고 무엇을 어떻게 바꿨는지가
제목만 읽어도 보이게 쓴다.

### 5. 확인 요청

초안 전문을 대화에 보여주고, 함께 다음을 밝힌다.

- 근거로 사용한 PR·커밋 목록
- 사용자에게 확인이 필요한 수치나 불확실한 서술
- Notion 에 append 할 위치 (어느 기간 항목 아래인지)

승인 없이 다음 단계로 넘어가지 않는다.

### 6. Notion 기록

**대상 페이지** — 사용자 개인 Notion 워크스페이스의 `주요 업무` 페이지.

`notion-search` 로 `주요 업무` 를 검색해 찾는다. 페이지 ID 는 이 문서에 적어두지 않는다.
후보가 여러 개면 제목과 URL 을 보여주고 사용자에게 고르게 한다.

검색 결과가 없으면 Notion MCP 연결이 끊겼거나 페이지가 커넥션에 공유되지 않은 것이다.
다른 페이지에 대신 쓰지 말고 사용자에게 알린다.

쓰기 전에:

1. `notion-fetch` 로 현재 페이지 내용을 읽어 기존 구조와 기간 항목을 확인한다.
2. Notion-flavored Markdown 문법을 추측하지 않는다. 토글·중첩 구조를 쓸 때는
   `notion-fetch` 에 `notion://docs/enhanced-markdown-spec` 을 넘겨 스펙을 먼저 읽는다.

기존 페이지 구조는 기간 불릿 아래에 작업별 토글을 두는 형태다.

```
- <기간> : <묶음 주제>
	- <하위 작업>
	<토글: 업무 제목>
		...PAAR 본문...
```

이 구조를 유지한다. 새 업무가 기존 기간에 속하면 그 기간 불릿 아래에 토글을 추가하고,
새 기간이면 기간 불릿을 먼저 만든다.

쓰기 방법:

- 기존 기간 아래에 넣을 때는 `notion-update-page` `command: update_content` 로
  해당 기간 불릿을 anchor 삼아 삽입한다.
- 페이지 맨 끝에 새 기간을 추가할 때는 `command: insert_content`,
  `position: {"type":"end"}` 를 쓴다.
- `allow_deleting_content` 는 쓰지 않는다. 하위 페이지 삭제 위험이 있는 작업은 중단하고
  사용자에게 묻는다.

기록 후 페이지 URL 을 알려주고, 실제로 반영됐는지 `notion-fetch` 로 확인한다.

## 품질 자기점검

Notion 에 쓰기 전 다음을 통과해야 한다.

- [ ] Problem 에 비즈니스 임팩트가 있다 (기술 현상만 있지 않다)
- [ ] Analyze 에 버린 대안과 그 이유가 있다
- [ ] Action 의 모든 항목이 커밋·PR·파일로 확인된다
- [ ] Result 의 모든 수치에 출처가 있다 (없으면 미실시로 명시)
- [ ] 근거 없는 형용사·부사가 없다 ("크게", "대폭", "획기적으로")
- [ ] 사용자 승인을 받았다

  다른 사람이 열 수 없다.
- 스킬 원본은 `~/source/jhahn/skills/paar-worklog` 하나이며 개인 레포
  `jonghyeok-97/jonghyeok-97` 로 관리한다. `~/.claude/skills/paar-worklog` 는
  심볼릭 링크이므로 그쪽을 직접 수정하지 않는다.
- 개인 레포에 있으므로 작업 중인 프로젝트 레포와 무관하게 항상 호출 가능하다.
  회사 레포에서 작업하다 호출해도 이 스킬 정의는 회사 레포에 커밋되지 않는다.
